你说得完全对。给实验组人为加一个提升再跑检验，本质上是"我预设了结论再证明这个结论"——这是循环论证，不是科学实验。
真实 A/B 测试的核心恰恰是：你不知道干预有没有用，所以才要做实验来验证。 我的做法把这一点彻底搞反了。
回到你的根本问题：离线项目如何在面试中证明会做 A/B 测试？
诚实答案是：证明不了你"跑过"AB 测试，但可以证明你"会设计"AB 测试。 这本身就是两个不同的考察点——面试官问 AB 测试，80% 在考设计，不是在考你有没有真的按过分流按钮。
所以第七阶段不应该叫"模拟 A/B 测试"，应该叫 "A/B 测试实验设计"——产出一份完整的实验方案文档。核心内容包括：

  1. 实验设计：实验单元、分流策略、对照组/实验组定义、实验周期
  2. 样本量计算：给定 MDE/α/Power，推导最小样本量，验证你的数据规模是否够
  3. 统计方法选型：为什么用 Z 检验而不是 T 检验，单尾还是双尾
  4. AA 校验（这个是唯一能用历史数据真正做的）：把历史用户随机分两组，证明指标在实验前无显著差异——验证分流机制是均匀的
  5. 决策框架：p < 0.05 怎么做，p > 0.05 怎么做，效应量多大才有业务意义

  这份文档本身就是作品集的一部分。面试时直接说：

  ▎ "竞赛项目没有线上环境，无法真正跑 A/B 测试。但我设计了一套完整的实验方案，包括样本量计算、随机化策略、统计方法选型、AA 校验和决策框架。如果需要，我可以在有线上环境的情况下直接落地执行。"

## 讨论结果，主要设计AB测试文档，配合朋友圈特征作为着手点。


### 但是其实我觉得我把范围拉得太窄了，因为这些数据集总共就是在1年内的数据，很明显没法完全覆盖现实生活中的朋友圈，如果我把范围拉得太窄的话，可能就会导致过度拟合。                                                                                                                                                                                  

● 你说得对。一年的数据窗口，朋友圈是不完整的——新朋友还没出现、老朋友的互动记录可能不在这期间内。把候选集硬约束在朋友圈里，测试集上的泛化会很差。

  但你的方向没错，只是朋友圈不该做硬约束，而该做软信号。

  换个思路：
  
  不是：只预测 A 的朋友会回流
  而是：A 的朋友圈特征作为权重，告诉模型"这个是朋友，关注一下"

  具体来说是给每条候选边 (A, B) 加一个特征维：A 和 B 的社交关系强度。比如：

  ┌──────────────────────┬──────────────────────────┬───────────┐
  │         特征         │ 朋友圈内 (B 是 A 的朋友) │ 朋友圈外  │
  ├──────────────────────┼──────────────────────────┼───────────┤
  │ is_friend            │ 1                        │ 0         │
  ├──────────────────────┼──────────────────────────┼───────────┤
  │ A→B 历史分享次数     │ 实际值                   │ 0         │
  ├──────────────────────┼──────────────────────────┼───────────┤
  │ A→B 最近一次分享距今 │ 实际天数                 │ -1 或 max │
  ├──────────────────────┼──────────────────────────┼───────────┤
  │ B 对 A 的历史响应率  │ B回流次数/A分享次数      │ 0         │
  └──────────────────────┴──────────────────────────┴───────────┘

  模型自己学：朋友圈特征重要 → 给朋友更高分；朋友圈特征不重要 → 这些特征的权重自动降下来。

  这跟你的想法一致——给朋友更大权重——但不会把范围拉窄。 LightGBM 和 GNN 都可以消化这些特征，而且不强依赖朋友圈完整性，缺了就填 0。

  要加这个 Block 吗？计算量很小，主要是对历史边做 groupby 聚合。

### 我在想，要不要把这个作为AB测试的一个着手点。                                                                                                                                                                                      

● 可以，而且这比"优惠券 A/B 测试"靠谱得多。理由：

  你有数据支撑。 朋友圈可以从 df_train_all 直接构建，友圈内/外的回流率差异也能直接算。A/B 测试设计书写的时候，用真实数据做基线，比凭空假设一个效应量有说服力。

  实验问题很自然：

  ▎ 预测回流用户时，给 inviter 朋友圈内的候选者加权，能否提升整体分享回流率？

  - 对照组 (Control)：GNN/LightGBM 正常预测，候选池为全局用户，不区分朋友/非朋友
  - 实验组 (Treatment)：预测时对 inviter 朋友圈内的候选者加权（如朋友 ×1.5），其他不变
  - 主指标：回流率（预测的 Top-K 用户中实际回流的比例）
  - 护栏指标：新用户覆盖比例（防止只推老熟人，错过潜在的社交扩展）

  你甚至能在离线数据里做一轮"观测性预分析"来支撑实验动机：

  从历史数据里统计：
  - 历史回流中，回流者是 inviter 朋友的占比？
  - 朋友 vs 非朋友的回流概率有显著差异吗？
  - 如果有 → 加权策略有实证依据，实验设计有说服力
  - 如果没有 → 那加权没必要，但实验设计书本身还是有价值

  这和之前讨论的结论一致——A/B 测试不出真实结果，但出一份有数据支撑的实验设计书。不同的是，这次的设计书里有一节写着"观测数据预分析：友圈内回流率 X%，友圈外回流率 Y%，差异 p=0.00X"，比纯假设强得多。

## 是的，所以在我们建模的时候最好是做出4份模型文件，那就两份LightGBM（ab），两份GNN（AB）。分别都要有朋友圈加权的AB测试，是这样。然后我们现在是不是需要开始给每个用户制作朋友圈了？来吧你先把你的想法和我说一下。  

思路如下：

  ---
  第一步：朋友圈定义

  从训练数据里，一条边 <A → 商品 → B> 就是"A 分享给了 B"。朋友圈的定义直接取这个关系：
  
  friend_circle[user_id] = 所有 user_id 分享过的 voter_id 的集合

  双向性先不强制：A 分享给 B，B 就在 A 的朋友圈里，但 A 不一定在 B 的朋友圈。后续建模时 inviter 侧取 inviter 的朋友圈，voter 侧取 voter 的朋友圈。

  ---
  第二步：产出三样东西

  ┌───────────────────┬─────────────────────────────────────────────────────┬───────────────────────────────────┐
  │       产物        │                        内容                         │               用途                │
  ├───────────────────┼─────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ friend_circle.pkl │ {user_id: [friend_id, ...]} 字典                    │ 预测时直接查 A 的朋友列表         │
  ├───────────────────┼─────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ 用户级朋友圈特征  │ 朋友圈大小、双向好友率、圈内平均活跃度等            │ 追加到 user_profile_enriched      │
  ├───────────────────┼─────────────────────────────────────────────────────┼───────────────────────────────────┤
  │ 边级朋友圈特征    │ (A, B) 的 is_friend、交互次数、最近交互时间、响应率 │ 追加到训练边特征，LightGBM 直接用 │
  └───────────────────┴─────────────────────────────────────────────────────┴───────────────────────────────────┘

  第三样最关键——is_friend 这个 0/1 特征就是你的 AB 测试变量。

  ---
  第三步：建模时的 AB 测试设计

  4 份模型文件的区别：

  ┌────────────────────────┬─────────────────────────────────┬────────────────┐
  │          模型          │           朋友圈特征            │      含义      │
  ├────────────────────────┼─────────────────────────────────┼────────────────┤
  │ LightGBM-A (Control)   │ 不含 is_friend 及朋友圈衍生特征 │ 基线，全局候选 │
  ├────────────────────────┼─────────────────────────────────┼────────────────┤
  │ LightGBM-B (Treatment) │ 含 is_friend + 朋友圈交互特征   │ 朋友加权       │
  ├────────────────────────┼─────────────────────────────────┼────────────────┤
  │ GNN-A (Control)        │ 图不加入朋友圈边权重            │ 基线           │
  ├────────────────────────┼─────────────────────────────────┼────────────────┤
  │ GNN-B (Treatment)      │ 朋友圈边赋予更高初始权重        │ 朋友加权       │
  └────────────────────────┴─────────────────────────────────┴────────────────┘

  控制变量的方式很干净：特征维度不同，其他全部一样（训练集、超参、评估指标）。唯一差异就是朋友圈信号有没有喂进去。

  ---
  第四步：预分析（实验设计书的实证部分）

  在加 Block 之前，先跑一个观测性统计来给 AB 测试提供动机：

  历史数据中：
  - 回流事件中有 X% 的 voter 在 inviter 的朋友圈里
  - 朋友圈内回流率 = a%，朋友圈外回流率 = b%
  - 差异是否显著（Z 检验）

  这个结果直接写进第七阶段的实验设计书里，证明加权策略有数据支撑。

  实施计划

  在当前 notebook 后面加一个 Block（或新建一个小 notebook），分 3 个 cell：
  1. 构建朋友圈：从 df_train_all 聚合，存 friend_circle.pkl
  2. 用户级特征：朋友圈大小、双向好友率，合并进 enriched 表
  3. 边级特征：is_friend、交互次数、响应率，存 edge_friend_features.pkl
  4. 预分析：跑一下圈内/圈外回流率对比
