## 零、前置说明：离线项目中的 A/B 实验边界

### 0.1 当前项目做了什么

| 已有的东西 | 本质 | 价值 |
|-----------|------|------|
| LGB-A vs LGB-B vs LGB-C AUC/MRR对比 | **模型消融实验 (Ablation Study)** | 验证"边级特征在表格模型中是否有增量贡献" |
| 预分析: 朋友圈内回流率 vs 圈外回流率 | **观测数据预分析 (Observational Pre-Analysis)** | 为实验假设提供实证依据 |
| MRR分场景拆解 | **分层评估 (Stratified Evaluation)** | 量化特征在不同子群的效果差异 |

这些是**实验设计的前置工作**, 不是实验本身。每个都正确且必要, 但合在一起不等于一个完整的 A/B 实验。

### 0.2 什么是真正的 A/B 实验

> 在受控条件下, 将实验单元**随机分配**到对照组和实验组, 对两组施加**不同的干预**, 在预先确定的**统计框架**下比较核心指标的差异。

四个要件缺一不可: **随机化** + **干预** + **预设指标** + **统计检验**。

### 0.3 离线环境下的诚实策略

本项目没有线上流量, 无法执行真实的随机分流。本文档分两层:

| 层次 | 内容 | 作用 |
|------|------|------|
| **线下层**: 离线统计验证 | 基于历史验证集做置换检验 + Bootstrap置信区间 | 在实际约束下得到最接近"实验"的统计推断 |
| **线上层**: 真实施部署方案 | 随机分流、样本量估算、护栏指标、决策规则 | 证明你能设计一个能上线的实验, 不只是跑验证集 |

## 一、第一步: 判断必要性

### 1.1 核心业务问题

> 在分享回流预测中, 引入**朋友圈行为信号** (inviter-voter历史交互频率、回流比率、最近互动时间) 能否在**不损害新用户冷启动**的前提下, 显著提升**老朋友回流的排序精度**?

### 1.2 为什么必须做 A/B 实验而不是直接上线?

| 原因 | 说明 |
|------|------|
| **反直觉的基线结果** | 预实验发现: LGB-B(含朋友圈) AUC=0.8606 **低于** LGB-A(不含) AUC=0.8957。加入更多信息后效果反而差 — 这不是bug, 是需要用实验严谨验证的"信号" |
| **72/28分裂效应** | 验证集72%的正样本在训练期有交互历史, 28%没有。任何区分"有无历史"的特征都会让模型偷懒: 对72%轻松判对, 对28%高置信度判错 |
| **MRR与AUC方向可能不一致** | AUC衡量全局排序质量, MRR@5衡量Top-5排序质量。场景1(老朋友)MRR=0.74的场景下, 朋友圈信号可能提升MRR但拖累AUC — 需要更精细的分析 |
| **结构信号 vs 行为信号的本质分歧** | 这不仅是模型对比, 更是在追问: 社交网络中"你在什么位置"(图拓扑)和"你实际做了什么"(交互行为)哪个更有预测力? |

### 1.3 实验假设

```
H₀ (原假设): 引入朋友圈行为信号后, 核心指标(加权MRR@5)无显著提升。
              即: μ_treatment - μ_control ≤ 0

H₁ (备择假设): 引入朋友圈行为信号后, 核心指标(加权MRR@5)有显著提升。
               即: μ_treatment - μ_control > 0
```

**单侧检验** — 我们只关心实验组是否**优于**对照组, 不关心是否更差 (如果更差, 在生产环境中不会上线)。

## 二、第二步: 定核心指标

### 2.1 指标体系 (三层)

```
                    ┌─────────────────────────────┐
                    │  核心指标 (Primary Metric)    │
                    │  加权 MRR@5                   │
                    │  = 0.724×MRR_老朋友 + 0.276×MRR_新朋友 │
                    └─────────────┬───────────────┘
                                  │
              ┌───────────────────┼───────────────────┐
              │                   │                   │
              ▼                   ▼                   ▼
    ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
    │ 辅助指标 #1      │ │ 辅助指标 #2      │ │ 辅助指标 #3      │
    │ MRR@5(场景1)    │ │ HITS@5(场景1)    │ │ Rank1占比(场景1) │
    │ 老朋友回流排序    │ │ 老朋友命中率      │ │ Top-1准确率      │
    └─────────────────┘ └─────────────────┘ └─────────────────┘
              │                   │                   │
              ▼                   ▼                   ▼
    ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
    │ 护栏指标 #1      │ │ 护栏指标 #2      │ │ 护栏指标 #3      │
    │ MRR@5(场景2)    │ │ 新朋友覆盖率     │ │ MRR-total方差    │
    │ 不能暴跌          │ │ 不低于对照组      │ │ 稳定性检查        │
    └─────────────────┘ └─────────────────┘ └─────────────────┘
```

### 2.2 为什么用加权MRR@5而不是AUC?

| 问题 | 解释 |
|------|------|
| AUC是全局排序指标 | 对电商推荐, 用户只看到top-N结果。AUC为0.89但top-5全错, 商业价值为零 |
| MRR@5对应真实场景 | 朋友圈分享栏最多展示5条推荐。True voter出现在第1位(1.0分) vs 第5位(0.2分) vs 不出现(0分) — 这个梯度映射到真实用户体验 |
| 加权处理72/28分裂 | 老朋友和新朋友场景的MRR天花板不同。加权避免模型在"容易的72%"上过度优化, 确保28%不被牺牲 |

### 2.3 护栏指标的定义

护栏指标是**不允许显著恶化的指标** — 如果实验组在这些指标上比对照组差, 即使核心指标达标也不上线。

| 护栏 | 阈值 | 理由 |
|------|------|------|
| 场景2 MRR@5 | 不低于对照组的90% | 不能以牺牲新用户体验为代价换老朋友指标 |
| 新朋友覆盖率 | 不低于对照组 | 不能减少向新用户推荐的总次数 |
| 预测延迟 P99 | 不超过对照组的120% | 朋友圈特征涉及额外查询, 延迟不能失控 |

## 三、第三步: 算前置参数

### 3.1 基线数据 (来自 LGB-A 离线评估)

| 参数 | 值 | 来源 |
|------|-----|------|
| 基线加权MRR@5 (μ_control) | 0.574 (0.724×0.74 + 0.276×0.14) | lgb_baseline.py 第9节 |
| 场景1 MRR标准差 (σ₁) | ~0.42 (估计, 基于rank分布) | mrr_breakdown.py |
| 场景2 MRR标准差 (σ₂) | ~0.25 (估计) | mrr_breakdown.py |
| 流量日均查询数 | ~3,000 (决赛测试集11.5万/38天) | share_final_test时间跨度 |
| 实验单元 | 一次分享查询 (inviter, item) | |
| 实验单元间独立性 | 近似独立 (同一用户多次查询存在相关性, 需用用户级聚类标准误) | |

### 3.2 效应量定义 — MDE (Minimum Detectable Effect)

**什么是MDE?** 你愿意接受的最小提升幅度。低于MDE的效应即使统计显著, 商业上也不值得推动一次上线(涉及开发、测试、风险)。

```
MDE 取决于两个判断:
  1. 商业意义: 提升多少才算"值得做"?
  2. 统计可行性: 在你的样本量下, 能检出的最小效应是多少?
```

**本项目设定:**

| 场景 | MDE (相对) | MDE (绝对) | 理由 |
|------|-----------|-----------|------|
| 整体加权MRR | +3% | 0.574→0.591 | 保守估计。MRR从0.574到0.591意味着每100次分享多对1.7次 — 对于日活千万的平台有意义 |
| 场景1 MRR (核心战场) | +5% | 0.74→0.777 | 场景1基数高, 天花板约0.85, 5%提升是务实目标 |
| 场景2 MRR (冷启动) | 不胜于恶化 | 不低于0.14 | 新朋友没有历史交互, 场景2本身就是硬骨头。允许"不提升", 不允许"恶化" |

### 3.3 样本量计算

**公式 (两样本比例/均值的单侧检验):**

```
n_per_group = (Z_α + Z_β)² × (σ₁² + σ₂²) / Δ²

其中:
  Z_α  = 1.645  (α=0.05, 单侧)
  Z_β  = 0.842  (β=0.20, Power=80%)
  σ²   = 各组方差
  Δ    = MDE (绝对效应量)
```

**计算过程:**

```
场景1 (老朋友):
  σ₁ = σ₂ ≈ 0.42 (MRR标准差)
  Δ = 0.74 × 0.05 = 0.037 (5%相对提升)
  n_per_group = (1.645 + 0.842)² × (0.42² + 0.42²) / 0.037²
              = 6.187 × 0.3528 / 0.001369
              = 2.183 / 0.001369
              ≈ 1,595 查询/组

整体加权MRR:
  σ ≈ 0.38, Δ = 0.574 × 0.03 = 0.0172
  n_per_group = (1.645 + 0.842)² × (0.38² + 0.38²) / 0.0172²
              = 6.187 × 0.2888 / 0.000296
              = 1.787 / 0.000296
              ≈ 6,040 查询/组
```

### 3.4 最终样本量参数

| 参数 | 值 | 说明 |
|------|-----|------|
| **α (显著性水平)** | 0.05 (单侧) | 允许5%概率错误拒绝H₀ (第一类错误) |
| **1-β (统计功效)** | 0.80 | 80%概率在效应真实存在时检测到它 (第二类错误=20%) |
| **MDE (绝对)** | 0.0172 (整体加权MRR) | |
| **MDE (相对)** | 3% 提升 | |
| **每组最少样本量** | 6,040 查询 | 基于MDE=3%, power=80%, α=0.05 |
| **若MDE收紧到2%** | 每组需 ~13,600 查询 | 样本量与Δ²成反比 — MDE减半, 样本量×4 |
| **数据可用性** | 验证集有~30,000正样本查询 | 样本量充足 |

### 3.5 实验时长估算

```
决赛测试集: 115,414查询 / 38天 ≈ 3,037 查询/天
所需总样本: 6,040 × 2组 = 12,080 查询 (最少)
最少天数: 12,080 / 3,037 ≈ 4 天
建议天数: 7-14 天 (覆盖完整的周周期, 消除星期效应)
```

### 3.6 α与β的博弈 — 面试加分项

```
α (Type I Error): 假阳性 — "实验组其实没用, 但我们错误地认为有用"
  后果: 上线了一个无效功能, 浪费开发资源

β (Type II Error): 假阴性 — "实验组其实有用, 但我们没检测出来"
  后果: 错过了一个能提升回流率的好策略

二者的取舍取决于错误的成本:
  - 如果上线成本高(涉及后端改造) → 收紧α (如α=0.01), 宁错过不上错
  - 如果错过成本高(竞品在抢用户) → 收紧β (如power=0.90), 宁可多测也不错失
  - 本项目建议 α=0.05, power=0.80 — 标准工业实践
```

## 四、第四步: 配置实验

### 4.1 实验单元与随机化

**实验单元:** 一次分享查询 = (inviter_id, item_id, timestamp)

**随机化策略:**
- **哈希分桶:** `bucket_id = hash(inviter_id + item_id) % 100`
  - 桶 0-49 → 对照组 A (若无历史交互数据, 使用纯用户画像+商品+拓扑特征)
  - 桶 50-99 → 实验组 B (额外获取朋友圈行为信号)
- **为什么用(inviter_id, item_id)而不是user_id哈希?** 同一个user的多次分享应分到同一组 — 避免同一个用户在不同组里看到不同的推荐质量(用户体验一致性)
- **为什么不用user_id单独哈希?** 有些用户只在特定商品上分享, 用user_id随机分可能让两组在商品分布上不平衡

**实际上: 考虑到这是推荐模型对比而非UI实验, 用户级分桶更合理:**
```
bucket_id = hash(inviter_id) % 100
桶 0-49 → 模型A (无朋友圈特征)
桶 50-99 → 模型B (含朋友圈特征)
```
理由: 同一个inviter的所有分享查询保持一致体验。如果A→C之间切换模型, inviter会困惑"为什么同样的分享有时推荐准有时不准"。

### 4.2 分流比例

```
对照组 A: 50% 流量
实验组 B: 50% 流量

为什么是50/50而非10/90?
  - 我们没有"风险不对称" — 两个模型都是离线验证过的, 不存在哪个更危险
  - 50/50最快收敛 — 在给定总流量下, 等分达到最高统计效力
  - 如果是线上新策略有风险, 才用 10/90 (小流量灰度), 逐步放量
```

### 4.3 分层抽样 (Stratification)

**分层变量:** inviter的朋友圈大小 (活跃度分层)

| 层 | 朋友圈大小 | 占比 | 分层理由 |
|----|-----------|------|----------|
| 低活跃 | 1-5人 | ~40% | 朋友少, 候选池小 → MRR天花板高 → 最容易从朋友信号获益 |
| 中活跃 | 6-20人 | ~35% | 中等朋友数 → 最大化区分度的战场 |
| 高活跃 | 21+人 | ~25% | 朋友多, 候选池大 → 最难排序 → 朋友行为信号最有价值 |

**为什么需要分层?** 如果随机分流导致实验组分配到更多高活跃用户(他们本身回流率就高), 就会产生辛普森悖论 — 实验组MRR更高, 但不是因为策略更好, 而是因为用户构成不同。

**实施方式:** 在每个层内独立随机分流。事后分析时对每层分别计算效应量, 做加权合并。

### 4.4 实验配置总览

```
┌──────────────────────────────────────────────────────────────┐
│                    A/B 实验配置卡片                            │
├──────────────────────────────────────────────────────────────┤
│  实验名称:   朋友圈行为信号对分享回流预测排序质量的影响          │
│  实验单元:   一次分享查询 (按inviter_id哈希分桶)                │

│  分层:       inviter朋友圈大小 (低1-5 / 中6-20 / 高21+)       │
│  分流比例:   50% 对照组 / 50% 实验组                           │
│  对照组 A:   LightGBM/GNN, 特征=用户画像+商品+图拓扑, 无朋友圈  │
│  实验组 B:   LightGBM/GNN, 特征=对照组+朋友圈边级行为特征       │
│  实验时长:   14天 (覆盖2个完整周周期)                           │
│  最少样本:   12,080 查询 (两组合计)                             │
│  分析方式:   分层置换检验 + Bootstrap 95%CI + 多重检验校正      │
└──────────────────────────────────────────────────────────────┘
```

### 4.5 OEC (Overall Evaluation Criterion) — 实验的最终裁判

**面试中面试官会追问: "多个指标方向不一致怎么办?"**

定义裁决规则:

```
主裁决:
  如果 加权MRR@5 的 p-value < 0.05 且 相对提升 ≥ MDE(3%)
  AND 护栏指标全部未触发 → 实验组胜出, 建议上线

护栏触发:
  如果 场景2_MRR_treatment < 0.9 × 场景2_MRR_control
  → 一票否决, 即使核心指标显著也不上线
  → 需要重新设计策略: "朋友圈信号只用于老朋友排序, 新朋友保留原逻辑"

不确定情况:
  如果 加权MRR@5 的 p-value < 0.05 但提升 < MDE(3%)
  → 统计显著但商业价值不显著 → 不建议上线, 继续优化
```

## 五、第五步: 统计方案

### 5.1 为什么不用简单的Z检验?

Z检验 (两样本比例检验) 的前提是**观测独立** — 但我们的数据中:
- 同一个inviter的多条查询相关 (共享同一个行为模式)
- 同一个voter出现在多个查询中
- 同一个item被多次分享

**违反独立性假设 → 标准误被低估 → p值过于乐观 → 假阳性率 > 5%。**

### 5.2 推荐方案: 用户级聚类Bootstrap

```python
算法: User-Level Clustered Bootstrap

1. 获取所有唯一 inviter_id
2. 重复 B=10,000 次:
   a. 从 inviter_id 中有放回抽样 N 个
   b. 取出这些 inviter 的全部查询
   c. 分别计算实验组和对照组的 加权MRR@5
   d. 记录差值 Δᵢ = MRR_treatment - MRR_control
3. 从 {Δ₁, Δ₂, ..., Δ_B} 的经验分布中:
   - 计算 95% 置信区间 (2.5%分位, 97.5%分位)
   - 计算 p-value = P(Δ ≤ 0) 的比例
4. 如果 95%CI 完全在 0 以上, 拒绝 H₀
```

### 5.3 辅助方案: 置换检验 (Permutation Test)

```python
算法: Permutation Test (Fisher精确检验的推广)

1. 对每个查询随机打乱"组别标签"(A或B), 保持各组样本量不变
2. 重新计算两组MRR的差值
3. 重复 10,000 次 → 得到 H₀ 为真时差值的零分布
4. 实际观测差值在零分布中的位置 → p-value
5. p-value < 0.05 → 拒绝 H₀, 实验组显著优于对照组
```

**Bootstrap和Permutation互补:** Bootstrap给出置信区间(Practical Significance), Permutation给出p-value(Statistical Significance)。

### 5.4 多重检验校正

我们在看多个指标 (加权MRR + 场景1 MRR + 场景2 MRR + HITS) — 做4次检验。如果每次都用α=0.05, 整体犯第一类错误的概率是多少?

```
P(至少一次假阳性) = 1 - (1 - 0.05)⁴ ≈ 18.5%
```

**用Bonferroni校正:** 对4个指标, 每个检验的α调整为 0.05/4 = 0.0125。

但Bonferroni过于保守。**推荐Holm-Bonferroni逐步法:**
1. 对所有指标的p值从小到大排序: p₁ ≤ p₂ ≤ p₃ ≤ p₄
2. p₁ 与 α/4 比较, p₂ 与 α/3 比较, p₃ 与 α/2, p₄ 与 α/1
3. 第一个不显著的停止, 后面的全部不显著

### 5.5 离线环境下的执行方案 (我们现在能做的事)

线下层: 基于验证集的分层置换检验

```python
输入: valid_lgb.pkl (验证集, 含LGB-A的特征矩阵和label)
      lgb_baseline_A.pkl, lgb_baseline_C.pkl (两个模型)

流程:
  Step 1: 提取验证集所有正样本查询 (inviter, item, true_voter, timestamp)
  Step 2: 对每个查询, 构造候选voter池 (inviter的全部训练期朋友 + 200随机补充)
  Step 3: 分别用模型A和模型C对候选打分
  Step 4: 计算每个查询的 MRR_A 和 MRR_C
  Step 5: 按inviter朋友圈大小分层
  Step 6: 每层内做 B=10,000 次用户级Bootstrap
          → 得到每层的 Δ_MRR 置信区间和p-value
  Step 7: 加权合并各层结果(Holm-Bonferroni校正)
  Step 8: 输出统计报告

输出:
  ┌──────────────────────────────────────────────────────┐
  │           A/B 实验统计报告 (离线验证)                   │
```

## 六、面试叙述框架

### 6.1 面试官问"你做过A/B实验吗"时的完整回答

**第1层 (20秒): 明确概念边界**
> "我首先要区分两个概念: 模型消融实验和真正的A/B实验。消融实验是离线评估中验证'去掉某个特征模型变差多少'; A/B实验是线上随机分流, 在受控条件下比较两组用户的真实行为差异。我两者都做了。"

**第2层 (60秒): 描述实验设计**
> "我的实验变量是'朋友圈行为信号是否作为模型输入特征'。对照组用纯用户画像+商品特征+图拓扑, 实验组额外加朋友圈交互频率、回流比率、最近互动时间。实验单元按inviter_id哈希分桶, 50/50分流, 按朋友圈大小分层。核心指标是加权MRR@5, 用0.724和0.276的权重分别对应老朋友和新朋友场景。MDE设为3%相对提升, power=80%, α=0.05单侧, 每组最少6,040个查询, 跑14天覆盖周周期。"

**第3层 (30秒): 统计方法的严谨性**
> "我不用简单的Z检验 — 因为同一用户的多条查询相关, 违反独立性假设。我用用户级聚类Bootstrap做置信区间估计, 用置换检验做显著性推断, 对多个指标做Holm-Bonferroni校正控制假阳性率。如果核心指标显著但新朋友场景MRR暴跌超过10%, 我设了护栏一票否决。"

**第4层 (20秒): 离线约束下的诚实**
> "因为我的项目是离线竞赛数据集, 没有线上流量, 我没有假装跑了一个线上实验。线下层我做了完整的预分析和分层置换检验作为统计验证, 线上层我写了完整的实验设计书包含样本量、分流、护栏指标和决策矩阵。如果需要我可以直接上线实施。"

### 6.2 面试官可能的追问及应对

**追问1: "为什么用MRR@5而不是AUC?"**
> "AUC是全局排序指标, 但朋友圈分享栏只展示5个推荐位。如果true voter排在top-1(得分1.0)和永远不在top-5(得分0)对用户体验的差异巨大。MRR@5直接量化这个商业损失。另外我们的预实验发现了一个关键现象: 有些特征提升AUC但拖累MRR — 因为72%的案例中模型轻松判断'老朋友', 但28%的新朋友场景被高置信度判错。AUC掩盖了这个问题, MRR分场景拆解揭露了它。"

**追问2: "MDE为什么设为3%? 2%不行吗?"**
> "可以, 但需要更多样本。MDE与样本量是平方关系: MDE从3%降到2%(减少了1/3), 样本量需要增加(3/2)²=2.25倍。我们的日均查询约3000条, 3% MDE需要14天。如果业务方认为2%的提升也值得上线, 我需要跑约32天。MDE最终是商业决策: 多少提升幅度值得投入一次上线的工程成本?"

**追问3: "如果核心指标显著, 但场景2 MRR恶化, 你怎么处理?"**
> "这正是护栏指标的用途 — 一票否决。核心问题是: 朋友圈信号只有对老朋友有效, 模型一旦看到这个信号, 就会系统性地给所有新朋友低分。解决方案是分而治之: 对老朋友用含朋友圈的模型B, 对新朋友(无历史交互)回退到纯画像模型A。这个组合策略在预分析中已被验证可行。"

## 八、附录: 关键公式速查

### 样本量计算
```
n_per_group = (Z_α + Z_β)² × (σ₁² + σ₂²) / Δ²
           = (1.645 + 0.842)² × (0.42² + 0.42²) / (0.74×0.05)²
           ≈ 1,595 查询/组 (场景1, 5%MDE)
```

### MRR 计算公式
```
MRR@K = 1/|Q| × Σ 1/rank(q)  if rank(q) ≤ K else 0

加权MRR = w₁ × MRR_场景1 + w₂ × MRR_场景2
        = 0.724 × MRR_场景1 + 0.276 × MRR_场景2
```

### Bonferroni 校正
```
α_adjusted = α / m  (m = 指标数量)
对于4个指标: α_adjusted = 0.05/4 = 0.0125
```

### Holm-Bonferroni 逐步法
```
p值排序后: 第i个检验的比较阈值为 α/(m-i+1)
第1个(最小p): α/4
第2个: α/3
第3个: α/2
第4个(最大p): α/1 = 0.05
```
